     Plan — Sync Tamagui Tokens, Fix Illustrations, Audit Button Tokens, and 
     Resolve ImagePicker Deprecation

     Context

     The app is running on a custom EAS dev client and screens are already
     migrated to Tamagui primitives. However, several token names referenced
     across components/illustrations/*.tsx and the auth/onboarding screens
     ($sand, $borderDefault, $night, $amber, $surface, $ai,
     $aiLight, $brandVerification, $verificationLight, $semDanger,
     $semWarning, $semSuccess) are not registered in
     constants/tamagui.config.ts (or its root copy at tamagui.config.ts).

     Consequences:
     - The onboarding illustrations render as black boxes because Tamagui
     falls back to transparent (and SVG fill="transparent" paints black
     in dark/inverted contexts) when an unknown token is referenced.
     - The primary buttons across auth screens use a mix of colors.brand.*
     constants and style={{ backgroundColor }}, which makes them bypass
     the Tamagui token system. The user wants these normalized so all
     backgrounds and radii use centralized Tamagui tokens (e.g.
     bg="$amber", br="$3").
     - components/forms/AvatarUploader.tsx uses the deprecated
     ImagePicker.MediaTypeOptions.Images enum and surfaces a deprecation
     warning on every Metro reload (Expo SDK 54 deprecation).

     This plan adds the missing tokens, rewrites illustrations to use
     already-defined equivalents (so they stop being black), normalizes the
     primary buttons to use $-token props, and switches the image picker
     to the new array-of-MediaType API.

     Architectural Rules (must follow)

     From CLAUDE.md:
     1. Never use standard React Native View / inline styles for structure.
     Use YStack/XStack/ZStack and Tamagui props.
     2. Never use Tailwind / NativeWind. Tamagui props only.
     3. Never hardcode hex in components. Use Tamagui design tokens
     (e.g. bg="$night", color="$amber").
     4. Both constants/tamagui.config.ts and root tamagui.config.ts must
     stay byte-equivalent at the token level (the babel/metro plugins
     resolve from project root, the app imports from constants/).

     Critical Files

     - constants/tamagui.config.ts (canonical, used by app/_layout.tsx)
     - tamagui.config.ts (root copy, used by babel/metro plugin
     withTamagui/@tamagui/babel-plugin)
     - components/illustrations/DiscoverIllustration.tsx
     - components/illustrations/AiMatchIllustration.tsx
     - components/illustrations/VerifiedIllustration.tsx
     - components/forms/AvatarUploader.tsx
     - screens/auth/RoleSelection.tsx (primary Continue button)
     - screens/auth/PhoneEntryScreen.tsx (primary Send OTP / Log in)
     - screens/auth/OtpVerify.tsx (primary Verify OTP)
     - screens/auth/Password.tsx (primary Continue)
     - screens/auth/ProfileScreen.tsx (primary Finish setup — kept in
     sync with StudentProfileScreen/TutorProfileScreen for now)
     - screens/auth/StudentProfileScreen.tsx (primary Finish setup)
     - screens/auth/TutorProfileScreen.tsx (primary Finish setup)
     - screens/onboarding/OnboardingScreen.tsx (primary Next / Get started)

     Step 2 — Rewrite illustrations to use only valid token names

     Each of the three illustration files is already structurally correct
     (YStack + react-native-svg primitives), but the file-header
     docstring comments in AiMatchIllustration.tsx and
     VerifiedIllustration.tsx reference $aiLight and
     $verificationLight as if they were defined — they are now defined
     in Step 1, so no renaming is needed; we only need to verify.

     The actual black-box issue comes from one token: VerifiedIllustration
     uses fill="$verificationLight" (line 35). With Step 1 added, this
     resolves correctly. No code change in illustration files is required
     as long as Step 1 is applied.

     If after Step 1 the illustrations still misbehave, the fallback is to
     use the long-form equivalents that are already defined (e.g.
     $bgPage, $bgSurface, $borderDefault, $brandAi,
     $brandAiLight, $brandVerification, $brandVerificationLight) — but
     the goal of Step 1 is to add the short aliases so the SVG code can
     keep using the readable token names.

     Step 3 — Normalize primary buttons across auth/onboarding screens

     The seven primary buttons (one per screen listed above) all currently
     use the pattern:

     <Button
       style={{ backgroundColor: canSubmit ? colors.brand.primary :
     colors.border.strong }}
       pressStyle={{ backgroundColor: canSubmit ? colors.brand.primary :
     colors.border.strong }}
       borderRadius={12}
       ...
     >

     Replace with centralized Tamagui tokens (per CLAUDE.md rule 3):

     <Button
       bg={canSubmit ? "$brandPrimary" : "$borderStrong"}
       pressStyle={{ bg: canSubmit ? "$brandPrimary" : "$borderStrong" }}
       borderRadius="$3"   // = 12px, from the existing radius token map
       ...
     >

     Radius-token mapping (already in constants/tamagui.config.ts):
     - borderRadius={10}  → borderRadius="$md" (or numeric 10)
     - borderRadius={12}  → borderRadius="$card" (or numeric 12 / $3)
     - borderRadius={14}  → borderRadius="$lg" (or numeric 14)
     - borderRadius={16}  → borderRadius="$4" (or numeric 16)
     - borderRadius={999} → borderRadius="$full" (or numeric 999 / $full)
     - borderRadius={9999}→ borderRadius="$full"
     - borderRadius={20}  → numeric 20 (no token for 20 yet — keep numeric
     to avoid adding a new token just for the onboarding slide frame)

     For consistency with the existing size/radius token table, the
     preferred mapping is the existing named tokens (e.g. $card for 12,
     $lg for 14, $full for 999). Buttons that use borderRadius={14} or
     borderRadius={20} (the slide frame and Finish setup) will keep
     their numeric value if no token exists at that exact size — this is
     the only exception to the token rule, and it's intentional (we
     don't want to inflate the radius scale with one-off values).

     For screens where the button color is the accent copper
     (colors.brand.accent) rather than primary night (the three profile
     "Finish setup" buttons: ProfileScreen, StudentProfileScreen,
     TutorProfileScreen), use bg="$brandAccent" / bg="$borderStrong".

     For the Send OTP / Log in button in PhoneEntryScreen.tsx (line
     232) and the Verify OTP button in OtpVerify.tsx (line 287), use
     bg="$brandPrimary" / bg="$borderStrong".

     For the Continue button in Password.tsx (line 228) and
     RoleSelection.tsx (line 136), use bg="$brandPrimary" /
     bg="$borderStrong".

     For the Next / Get started button in OnboardingScreen.tsx (line
     136), use bg="$brandPrimary".

     The "Change" / "Forgot password" / "Show password" / skip / tab-toggle
     buttons are all secondary and use backgroundColor="transparent"; they
     already use a string literal ("transparent") and don't need
     tokenization — leave them as-is.

     Step 4 — Fix expo-image-picker deprecation in AvatarUploader.tsx

     Replace:

     mediaTypes: ImagePicker.MediaTypeOptions.Images,

     with the new array-of-MediaType API (per the deprecation note in
     node_modules/expo-image-picker/build/ImagePicker.types.d.ts):

     mediaTypes: ['images'],

     MediaType is a TypeScript string-union type ('images' | 'videos' | 
     'livePhotos'), not a runtime enum, so the runtime value is the string
     literal 'images'. This matches the SDK 54 migration guide.
