## 1. 🔴 Admin sign-in section is internally contradictory (Step 6)

**What the plan says**:

> **No Firebase Auth for admins.** The "Log in" tab detects that the input contains `@` (treats it as email) and shows the `AdminLoginForm` inline below the phone input. On submit:
>
> 1. Query Firestore: `collection("admins").where("email", "==", normalizedEmail).limit(1).get()`.
> 2. If a doc exists, compare `bcrypt`-equivalent (we use `firebase/auth` `signInWithEmailAndPassword` against a Firebase Auth user we provision for each admin — see below) or plain SHA-256 of submitted password against the stored hash. **For v1 we use the simpler approach:** each admin's `admins/{adminId}` doc has a `passwordHash` field (SHA-256 of password + salt).

**The contradiction**:

- The first sentence says "**No Firebase Auth for admins**".
- The second sentence then says we *do* use `signInWithEmailAndPassword` "against a Firebase Auth user we provision for each admin".
- The third sentence says "**For v1 we use the simpler approach:** SHA-256 match against Firestore."
- Step 7's auth guard says `app/(app)/_layout.tsx` should redirect to `phone-entry` if `user` is null **or** `adminProfile` is null. But `auth.currentUser` is null for SHA-256-matched admins, so the guard would kick the admin back to login on every page render.

**Required fix**: pick one v1 admin path and stick to it. Recommendation: **SHA-256 match against Firestore, no Firebase Auth session for admins** (matches user's "directly match stored credentials" answer). Update the guard to check `user || adminProfile`, and update `signOut()` to clear the admin branch.

## 2. 🔴 Phone+password sign-in section contradicts itself (Step 12)

**What the plan says**:

> ### Step 12 — Phone+password sign-in (v1 caveat)
>
> Because Firebase Auth Phone provider does not natively support password (it always uses OTP), v1 phone+password sign-in works as:
>
> 1. User enters phone + password.
> 2. Service fetches `users/{uid}` (looked up by phone) and verifies the SHA-256 hash of the submitted password matches the stored `passwordHash` …
> 3. Service calls `signInWithPhoneNumber(auth, phone, recaptchaVerifier)`.
> 4. Service immediately calls the resulting `ConfirmationResult.confirm(<auto-generated code we sent to the user's own SMS or our backend>)`.
>
> This is awkward. **The v1 implementation skips step 3-4** and instead uses a **Cloud Function** `signInWithPhonePassword` that mints a custom token. **However, Cloud Functions setup is out of scope for this plan.** So v1 phone+password sign-in is documented as **disabled in the UI** with a tooltip: "Phone + password sign-in is coming soon. Use OTP instead."

**The contradiction**: the plan describes a 4-step flow, then says the v1 impl skips steps 3-4 and uses a Cloud Function, then says the Cloud Function is out of scope, so it disables the UI. The reader can't tell which path was actually built.

**Required fix**: delete the 4-step sketch. Keep only the v1 conclusion: phone+password is disabled in v1, tooltip "Coming soon. Use OTP instead", future work is a Cloud Function.

## 3. 🟠 User doc creation timing is unclear

**What the plan says**: The PhoneEntry → OtpVerify → Password flow creates the Firebase Auth `User` (after OTP verify). But the actual `users/{uid}` document with `role` and `fullName` is only written in `StudentProfileScreen.handleSubmit` / `TutorProfileScreen.handleSubmit` (Step 8).

**The problem**: the auth-bootstrap in Step 7 fetches `users/{uid}` to get `role` before the user has completed profile setup. So on first login:

- `auth.currentUser` exists (just verified OTP)
- `users/{uid}` doc does not exist yet
- `authStore.role` stays `null`
- `useRedirectAfterAuth` doesn't know where to send the user

The plan's `redirectAfterAuth` falls back to `/(auth)/role-selection` in that case (per the `lib/README.md` snippet), but the **layout-level guard** in Step 7 also reads `role` and may bounce the user. If the guard checks `user && !role` and redirects to role-selection, that's fine; if it checks `user && role` and redirects to `/(app)/{role}`, the new user is stuck because the dashboard route requires `role`.

**Required fix**: spell out the guard logic explicitly. Recommend:

- `app/(auth)/_layout.tsx`: if `user && role` → `/(app)/{role}`. Otherwise render auth children.
- `app/(app)/_layout.tsx`: if `!user && !adminProfile` → `/(auth)/phone-entry`. Otherwise render dashboard children. (Do NOT require `role` here — the dashboard screen can show a "finish your profile" empty state if `role` is null.)

## 6. 🟠 Stale reference to `getReactNativePersistence` requires `firebase@>=10` AND `firebase/auth` modular import (correct, but version is critical)

The plan says:

> `npx expo install firebase react-native-webview`

`npx expo install` will resolve the SDK-54-compatible version of `firebase`. As of the audit, that is `firebase@^10.13.x` or later. **`getReactNativePersistence` is exported from `firebase/auth` (modular)**. The plan's code sample uses the modular import correctly. ✅

But the plan also says:

> After install, also add `getReactNativePersistence` registration on the auth singleton. No `google-services.json` is needed because we are using the JS SDK.

This is correct but a new reader will ask: **"If we're using the JS SDK, do we still need to rebuild the dev client when adding `firebase`?"** The answer is **no for `firebase` itself** (it's pure JS), **yes for `react-native-webview`** (it has native code). The plan addresses this implicitly but should be louder:

```bash
# After install:
npx expo install firebase        # pure JS — no rebuild needed
npx expo install react-native-webview   # has native code — REBUILD dev client
```

## 7. 🟠 `recaptcha-container` is a React Native `<View>`, not a DOM element

**What the plan says**:

> `recaptchaVerifier` is built via `new RecaptchaVerifier(auth, "recaptcha-container", { size: "invisible" })` where `#recaptcha-container` is an empty `<View>` rendered once at the top of `app/_layout.tsx`.

**The problem**: `RecaptchaVerifier` in `firebase/auth` is a **web** API. It expects a DOM element ID and injects an iframe. In a React Native environment, the `firebase/auth` JS SDK uses `react-native-webview` to host a hidden webview and re-implements `RecaptchaVerifier` as a `ReactNativeFirebaseRecaptchaVerifier` style shim (or the legacy `applicationVerifier` callback for newer SDK versions).

For SDK 10+, the documented pattern is:

```ts
import { PhoneAuthProvider } from "firebase/auth";

// In the PhoneEntryScreen:
const phoneProvider = new PhoneAuthProvider(auth);
const verificationId = await phoneProvider.verifyPhoneNumber(
  { phoneNumber: `+977${phone}`, session: undefined },
  // 👇 the second arg is the applicationVerifier
);

await confirmationResult.confirm(code);
```

For the v1 JS SDK path, you pass an `applicationVerifier` constructed as:

```ts
import { PhoneAuthProvider } from "firebase/auth";
const provider = new PhoneAuthProvider(auth);
const id = await provider.verifyPhoneNumber(
  { phoneNumber: `+977${phone}` },
  recaptchaVerifier, // <-- this is a `ApplicationVerifier` instance
);
```

Where `recaptchaVerifier` is built using the `react-native-firebase-recaptcha` module OR a manual wrapper. **The plain web `new RecaptchaVerifier(auth, "recaptcha-container", …)` will throw `auth/argument-error` in React Native** because there is no DOM.

**Required fix**: in Step 5, the plan must install `react-native-firebase-recaptcha` (or use the `firebase/auth/cordova` build, which is what the JS SDK auto-uses on RN) and build the verifier via the RN-aware factory, not the web `RecaptchaVerifier` constructor. The hidden `<View id="recaptcha-container">` is not how this works.

**Recommended minimal v1 path**: use the `firebase/auth` modular API. The library's React Native build auto-detects RN and provides `signInWithPhoneNumber` with a built-in `RecaptchaVerifier` shim that hooks into `react-native-webview`. The `applicationVerifier` argument is optional in that case.

```ts
import { signInWithPhoneNumber } from "firebase/auth";

// No recaptchaVerifier argument — RN build handles it via the bundled webview
const confirmationResult = await signInWithPhoneNumber(auth, `+977${phone}`);
```

This is the path that works today in Expo dev-client + SDK 54. The plan should adopt this.

## 8. 🟡 Ambiguous: where does the admin doc live in Firestore?

**What the plan says**: `match /admins/{adminId}` with `allow read: if request.auth != null`.

**The ambiguity**: the client-side credential match requires the user (who is not yet signed in via Firebase Auth) to read the `admins` collection. If `request.auth != null` is the rule, the unsigned-in admin user cannot read their own row. The `match /{document=**} { allow read, write: if false; }` catch-all then denies it.

**The result**: the v1 client-side admin login will fail with `permission-denied` at the first Firestore read.

**Required fix**: either

1. Allow `read` of `admins` for everyone (security hole, but acceptable for v1 demo) and add a comment saying "TODO: replace with Cloud Function in v2"; OR
2. Make admin login a 2-step flow: (a) sign in anonymously via Firebase Auth, (b) then read `admins` and match.

Option (2) is more secure. Option (1) is simpler and matches the user's "demo" framing.

**Recommended**: option (1) for v1, with a clear comment and a v2 ticket.

## 10. 🟡 Ambiguous: `Role` type — does it include `"admin"`?

`lib/registration.ts` defines:

```ts
export type Role = "student" | "tutor";
```

The plan's `types/user.ts` says:

> - `Role`, `UserProfile`, `TutorProfileFields`, `StudentProfileFields`, `AdminProfile`

But the user picked the role via the `RoleSelection` screen, which only has "Student" and "Tutor". The admin role is granted by **email match in Firestore**, not by the signup flow. So:

- `Role = "student" | "tutor"` is correct for the user collection's `role` field.
- `AdminProfile` is a separate type living in the `admins` collection. `authStore.adminProfile` is the in-memory representation.

**Required fix**: spell this out in Step 4 (authStore) — `adminProfile` is orthogonal to `role`, not a value of `role`. Otherwise a future reader will try to add `"admin"` to the `Role` union and break the RoleSelection screen.

## 14. 🔴 CRITICAL OVERRIDE — Wrong Firebase SDK (June 12, 2026, post-audit)

**Added after the original 9-finding audit was applied.**

The corrected plan still chose the **Firebase JS SDK** (`firebase` npm package) on the assumption that "the team's existing READMEs assume JS SDK". This is wrong for an Expo dev-client production app and was caught in review.

### What the override changes

- **Drop**: `firebase` (JS SDK), `react-native-webview`, the `RecaptchaVerifier` shim, the `connectFirestoreEmulator` JS pattern, the `process.env.EXPO_PUBLIC_FIREBASE_API_KEY` reads.
- **Add**: `@react-native-firebase/app`, `@react-native-firebase/auth`, `@react-native-firebase/firestore`. These hook into the native Android/iOS Google Play Integrity / APNs verification paths. **No webview, no reCAPTCHA, no invisible iframe.**
- **Add**: `google-services.json` at the project root (Android) and `GoogleService-Info.plist` (iOS) — already partially configured; the SHA-1 fingerprint is in the Firebase Console from the credentials manager output.
- **Add**: `expo-build-properties` config plugin (required by RNFirebase 21.x on Expo SDK 54 for the new architecture).
- **Update**: `app.json` — `android.googleServicesFile: "./google-services.json"`. No plugin entry needed (RNFirebase v21 auto-initializes from `google-services.json` at native build time).
- **Update**: the env vars in `.env` become **mostly unused**. RNFirebase reads from `google-services.json` at native build time, not from `process.env` at runtime. Only `EXPO_PUBLIC_FIREBASE_USE_EMULATOR` stays (it's read by a small `services/firebase/emulator.ts` we add).

### Why the JS SDK is the wrong choice for this app

| Concern | JS SDK (`firebase`) | Native SDK (`@react-native-firebase/*`) |
|---|---|---|
| Phone auth on Android | Requires `react-native-webview` + invisible reCAPTCHA iframe | Native `auth().signInWithPhoneNumber()` — uses Google Play Integrity for automatic device verification |
| Recaptcha on iOS | Same webview dance, plus iOS-Safari cookies | Native — no browser dependency |
| Runtime config | Read from `process.env` at runtime | Read from `google-services.json` at native build time |
| Source of truth | Two: `.env` AND Firebase Console | One: `google-services.json` (Android), `GoogleService-Info.plist` (iOS) |
| `signInWithPhoneNumber` API | 4-arg with `applicationVerifier` | 1-arg: `auth().signInWithPhoneNumber(phoneNumber)` |
| Offline behavior | ReCAPTCHA iframe needs a network round-trip | No webview, no network round-trip for verification |
| Expo dev-client | Supported but with caveats (webview native module) | First-class supported since RNFB 20.x |

### Status

All other audit fixes (1–13) still apply — the route-guard logic, the `Step 3.b` `RoleSelection` bug fix, the admin SHA-256 flow, the `git rm` command, the v1 admin rule, the `persistProfile` role-set call, the phone+password UI disable, and the file-create list are all SDK-agnostic and remain.

The plan in `firebase-auth-plan.md` will be rewritten to use the native SDK on the next pass.
