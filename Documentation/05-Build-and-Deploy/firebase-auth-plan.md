# EdumentX — Firebase Auth + Firestore + Role Dashboards (Phase 3)

## Context

The app has 7 polished auth/onboarding screens (PhoneEntry, OtpVerify, CreatePassword, RoleSelection, StudentProfile, TutorProfile, Onboarding) wired through Expo Router, but **every "submit" is a placeholder `Alert`**. The registration state shim `lib/registration.ts` carries the form data between screens but never persists it.

This phase connects the flow end-to-end:

1. **Phone OTP** via Firebase Phone Auth (sign-up path).
2. **Email/phone + password** sign-in (existing "Log in" tab) — looks up against the same Firebase Auth users.
3. **Admin sign-in** through the same "Log in" tab — **no Firebase Auth**. The email/phone + password are matched against an `admins` collection in Firestore using a SHA-256(salt + password) hash check. On success we set `authStore.adminProfile` and route to the admin dashboard. (Production-safe replacement is a Cloud Function — out of scope for v1, see `Documentation/04-Firebase/phase-3-notes.md`.)
4. **Firestore persistence** of the user profile at `users/{uid}` with a `role` field and a per-role subcollection (`tutorProfile`, `studentProfile`).
5. **Three simple dashboards** (Student, Tutor, Admin) — just enough to prove the auth + role-routing works. No bookings, no messaging, no map, no tutor search. Each dashboard shows the user's profile (avatar, name, role, key fields) and a Sign out button.
6. **Auth guard** on the root layout: signed-in users with a `role` skip the auth stack and go to their dashboard; signed-out users are kept out of dashboard routes.
7. **Babel fix** for the previous session's `installTurboModule called with 0 arguments` crash — add `react-native-worklets/plugin` to `babel.config.js` (it must be the **last** preset, after `nativewind/babel`).

The plan also removes a bug found during exploration: `RoleSelection` never writes the role to the registration shim, and `screens/auth/ProfileScreen.tsx` is dead code.

The READMEs in `lib/`, `hooks/`, `store/`, `services/`, `types/` describe a future "Phase 4" layout with Zustand. We are not building Phase 4 in this plan. We will follow those README contracts where it costs nothing (e.g. folder structure under `services/firebase/`) and ignore them where they would force a Zustand migration (the registration shim stays; we add a new `authStore` as a small standalone module that the layout and screens import directly).

## Architectural Rules (must follow, from CLAUDE.md)

1. Standard React Native primitives only (`View`, `Text`, `Pressable`, `TextInput`, `ScrollView`).
2. **Never reintroduce Tamagui** — the `tamagui.config.ts` files and `@tamagui/*` packages stay out.
3. **No hardcoded hex** outside `components/illustrations/*` — use Tailwind classes.
4. **Firestore SDK choice:** use the official **Native React Native Firebase** modules (`@react-native-firebase/app`, `@react-native-firebase/auth`, `@react-native-firebase/firestore`) from https://rnfirebase.io/. **Do NOT use the Firebase JS SDK (`firebase` npm package) and do NOT install `react-native-webview`** for an invisible reCAPTCHA container.
   - **Why native, not JS**: the JS SDK's `signInWithPhoneNumber` requires a `RecaptchaVerifier` to render an invisible reCAPTCHA iframe. In a mobile app there is no DOM, so the JS SDK requires `react-native-webview` to host a hidden webview for the iframe. This is fragile on Android (cookie / Play Services conflicts) and adds an extra native module. RNFirebase calls into the native `FirebaseAuth` SDK, which uses **Google Play Integrity** on Android and APNs on iOS for automatic device verification — no webview, no reCAPTCHA, no `applicationVerifier` argument.
   - **Source of truth**: `google-services.json` (Android) and `GoogleService-Info.plist` (iOS) at the project root, generated by the Firebase Console when the Android app is registered. The SHA-1 / SHA-256 fingerprints from `eas credentials` are already in the Firebase Console (verified June 12, 2026).
   - **RNFirebase 21.x on Expo SDK 54** supports the new architecture and `expo-dev-client`. Install via `npx expo install` (Expo routes through `expo-build-properties` to set the Android compile SDK + NDK ABI filters correctly).
   - The `EXPO_PUBLIC_FIREBASE_*` env vars are **mostly unused** for RNFirebase — the native SDK reads config at native-build time, not at JS runtime. We keep `EXPO_PUBLIC_FIREBASE_USE_EMULATOR` in `.env` for the small `services/firebase/emulator.ts` shim that flips a flag at JS runtime.

   Trade-off accepted: RNFirebase is a native module, so every dev-client rebuild that changes `@react-native-firebase/*` versions requires `eas build --profile development --platform android --clear-cache`. This is the same cost as any other native module (e.g. `react-native-reanimated`, `react-native-webview`) and is offset by the simpler phone-auth API and the absence of webview fragility.

## Approach

### Step 0 — Babel fix for `installTurboModule` crash

`react-native-reanimated@~4.1.1` (installed) depends on `react-native-worklets@0.5.1` registering its own TurboModule. With `newArchEnabled: true` (already on in `app.json`), the babel transform for worklets must run. Without it, the JS bundle calls `TurboModuleRegistry.getEnforcing(...)` with no module registered, which is exactly the `installTurboModule called with 0 arguments` error from the previous session.

```js
// babel.config.js
module.exports = function (api) {
  api.cache(true);
  return {
    presets: [
      ["babel-preset-expo", { jsxImportSource: "nativewind" }],
      "nativewind/babel",
      "react-native-worklets/plugin", // MUST be last
    ],
  };
};
```

After this change, `npx expo start -c` should boot without the TurboModule error and gesture-handler should be importable. (Note: this is independent of the Firebase work and is included in this plan because it blocks everything else.)

### Step 3 — Firebase is already initialized (no `services/firebase/config.ts` needed)

**This is the big difference from the JS-SDK plan.** With `@react-native-firebase/*`, the SDK auto-initializes from `google-services.json` at native-build time. There is no `initializeApp(...)` call in JS, no `getAuth(app)` singleton, no `connectFirestoreEmulator`. The native code does it all.

The two pieces we DO write are:

- `services/firebase/errors.ts` — a small `formatFirebaseError(code)` that maps the standard Firebase Auth + Firestore error codes to user-facing strings. Pure function, no imports from `firebase/*`.
- `services/firebase/emulator.ts` — a one-time boot shim that reads `EXPO_PUBLIC_FIREBASE_USE_EMULATOR` and calls `firestore().useEmulator('127.0.0.1', 8080)` if it's `"true"`. Imported once at the top of `services/firebase/firestore.ts` (or in `AuthBootstrap`).

`firestore()` and `auth()` are imported **per-call** from the native modules — no singletons, no initialization order to worry about. The native side guarantees readiness.

```ts
// services/firebase/firestore.ts (sketch)
import firestore from '@react-native-firebase/firestore';
import { EXPO_PUBLIC_FIREBASE_USE_EMULATOR } from '@/lib/env';

if (EXPO_PUBLIC_FIREBASE_USE_EMULATOR === 'true') {
  firestore().useEmulator('127.0.0.1', 8080);
}

export const db = firestore;
```

### Step 4 — Auth store (`store/authStore.ts`)

Standalone external store (no Zustand yet — keeping the pattern of `lib/registration.ts`):

```ts
import type { FirebaseAuthTypes } from '@react-native-firebase/auth';

type AuthState = {
  user: FirebaseAuthTypes.User | null;
  role: Role | null;
  isLoading: boolean;
  confirmationResult: FirebaseAuthTypes.ConfirmationResult | null;
  // adminProfile is orthogonal to `role`. `role` is the user's self-selected
  // account type ("student" | "tutor") written at /users/{uid}.role. Admins
  // never go through the signup flow; they live in the separate /admins
  // collection and are matched on login by SHA-256 hash. When `adminProfile`
  // is set, `user` and `role` are both null.
  adminProfile: AdminProfile | null;
};
```

Exposes `useAuth(selector)` and an imperative `authStore.update({...})`. This is the single source of truth for "who is the current user." `onAuthStateChanged` in `AuthBootstrap` (Step 7) pushes user/role into it.

### Step 5 — Auth service (`services/firebase/auth.ts`)

All functions use the **native** `@react-native-firebase/auth` API. The RNFirebase `auth()` instance is a per-call proxy — no singleton, no initialization order.

Functions:

- `sendPhoneOtp(phoneE164)` → calls `auth().signInWithPhoneNumber(phoneE164)` and stores the returned `confirmation` object in `authStore.confirmationResult`. **No `RecaptchaVerifier`, no `applicationVerifier`, no webview.** RNFirebase uses Google Play Integrity (Android) and APNs (iOS) for automatic device verification. On Android without Play Services (e.g. an emulator without GApps) the call will fail with `auth/operation-not-allowed` or `auth/app-not-authorized`; see the verification list in `04-Firebase/phase-3-notes.md §6` for the emulator setup workaround.
- `verifyOtp(code)` → reads `authStore.confirmationResult`, calls `.confirm(code)`, returns the resulting Firebase `User`. On success, the `onAuthStateChanged` listener in `AuthBootstrap` pushes the user into `authStore`.
- `signInWithAdminCredentials(email, password)` → admin path. Fetches `admins/{adminId}` by `email` and compares the submitted password's SHA-256 hash to the stored `passwordHash` (see Step 6 for salt + hash format). On match, sets `authStore.adminProfile`. **No Firebase Auth session is created for admins** — they live in a separate `admins` collection and the route guard accepts either `user || adminProfile`.
- `signInWithPhonePassword(phone, password)` → **not implemented in v1**. The "Log in" tab shows a tooltip "Phone + password sign-in is coming soon. Use OTP instead." See Step 12.
- `signOut()` → if `user` is set, calls `auth().signOut()`, then `authStore.reset()` (clears `user`, `role`, `confirmationResult`, `adminProfile`, sets `isLoading` to `false`). After reset, route to `/(auth)/phone-entry`.
- `linkPasswordToCurrentUser(password)` → calls `currentUser.updatePassword(password)` (RNFirebase method on the `User` instance) after the phone-auth account is created. This is the post-OTP step that gives users a future "Log in with phone+password" capability (password is stored as SHA-256(salt + password) in `users/{uid}/authCredential` for v1 — bcrypt upgrade in v2).
- `subscribeToAuthChanges(callback)` → returns the unsubscribe function from `auth().onAuthStateChanged(callback)`. Used by `AuthBootstrap` to keep `authStore` in sync with the native auth state.

### Step 6 — Admin sign-in (SHA-256 match, no Firebase Auth)

**Single v1 approach, no contradiction**:

1. The "Log in" tab detects that the input contains `@` (treats it as email) and shows the `AdminLoginForm` inline below the phone input.
2. On submit, the service runs `signInWithAdminCredentials(email, password)` (see Step 5).
3. The service does `collection("admins").where("email", "==", normalizedEmail).limit(1).get()` and reads the matching `admins/{adminId}` doc.
4. The doc has the shape `{ email, displayName, role: "admin", salt, passwordHash, createdAt, updatedAt }`. The `passwordHash` is `sha256(salt + ":" + password)`.
5. The service computes the same hash with the same salt and compares with `timingSafeEqual`. (Use a constant-time comparison helper to avoid timing attacks.)
6. On match: set `authStore.adminProfile = { id: adminId, email, displayName, role: "admin" }` and navigate to `/(app)/admin`.
7. **No Firebase Auth session is created for admins.** The route guard sees `user === null && adminProfile !== null` and allows the admin through.

**Seed script** (`scripts/seedAdmins.ts`): a one-off node script the user runs once to populate `admins/{id}` docs. For v1 demo data, the seed creates one admin: `admin@edumentx.dev` / `Admin@123`. (The script also generates the salt and hash; the password is never written in plaintext to the seed output or to git.)

**v1 security caveat (acknowledged)**: client-side admin credential match requires the `admins` collection to be publicly readable. See Step 10 for the Firestore rule. This is acceptable for the v1 demo; for production we will replace it with a **Cloud Function** `matchAdmin(email, password) → customToken` that signs the user in via `signInWithCustomToken`. The Cloud Function setup is tracked in `Documentation/04-Firebase/phase-3-notes.md` as a v2 ticket.

### Step 7 — Auth bootstrap + route guards

`app/_layout.tsx` becomes:

```tsx
<GestureHandlerRootView>
  <SafeAreaProvider>
    <AuthBootstrap>
      <Stack>
        <Stack.Screen name="(auth)" />     {/* onboarding, phone-entry, otpverify, etc. */}
        <Stack.Screen name="(app)" />      {/* student, tutor, admin dashboards */}
      </Stack>
    </AuthBootstrap>

    <StatusBar style="dark" />
  </SafeAreaProvider>
</GestureHandlerRootView>
```

**No reCAPTCHA infrastructure is needed.** The native `@react-native-firebase/auth` SDK uses Google Play Integrity (Android) and APNs (iOS) for automatic device verification. We pass **no** `applicationVerifier` to `auth().signInWithPhoneNumber(phone)`. (See Step 5 for the rationale.)

`AuthBootstrap` is a tiny client component that:
1. Reads `authStore.isLoading` (starts `true`).
2. Subscribes to `onAuthStateChanged(auth, callback)`.
3. On user change, fetches the `users/{uid}` doc to get `role`, sets `authStore.user/role/isLoading`.
4. Once `isLoading` is `false`, calls `useRedirectAfterAuth()` (a separate hook) which routes based on state.

**Route guard spec (must be implemented exactly this way to avoid the post-OTP, pre-profile deadlock)**:

- `app/(auth)/_layout.tsx` — if `user && role` → `router.replace(/(app)/{role})`. Otherwise render auth children. **Important**: do **not** redirect when `user && !role` — that is the post-OTP, pre-profile state and the user must be able to navigate through `/(auth)/role-selection` and `/(auth)/profile-{role}`.
- `app/(app)/_layout.tsx` — if `!user && !adminProfile` → `router.replace("/(auth)/phone-entry")`. Otherwise render dashboard children. **Do NOT require `role` here** — the dashboard can render a "finish your profile" empty state if `role` is null (defensive; in practice the user should never reach here without a role).
- `useRedirectAfterAuth()` for the index route (`app/index.tsx`): if `user && role` → `/(app)/{role}`; else if `adminProfile` → `/(app)/admin`; else → `/(auth)/onboarding` (first run) or `/(auth)/phone-entry` (returning user).

### Step 8 — Profile persistence

In `StudentProfileScreen.handleSubmit` and `TutorProfileScreen.handleSubmit`, after the existing local validation and `registration.updateProfile(...)` call, do (modular v22+ API — the namespaced `firestore().collection().doc().set()` form is deprecated):

```ts
import { getApp } from '@react-native-firebase/app';
import {
  getFirestore,
  doc,
  setDoc,
  serverTimestamp,
} from '@react-native-firebase/firestore';

async function persistProfile(role: Role) {
  const db = getFirestore(getApp());
  const u = auth().currentUser;
  if (!u) throw new Error("No authenticated user");

  await setDoc(doc(db, 'users', u.uid), {
    uid: u.uid,
    phone: u.phoneNumber,
    fullName,
    email,
    role,
    createdAt: serverTimestamp(),
    updatedAt: serverTimestamp(),
  }, { merge: true });

  // Student / tutor profile lives in a subcollection so re-saving on
  // "Edit profile" doesn't churn auth metadata on the parent user doc.
  await setDoc(doc(db, 'users', u.uid, `${role}Profile`, 'default'), {
    ...roleSpecificFields,
    updatedAt: serverTimestamp(),
  }, { merge: true });
}
```

After successful write: navigate to the appropriate dashboard.

### Step 8.b — Email + password sign-in (free email verification)

> **Update (June 19, 2026)** — added as a third sign-in path alongside phone OTP and Google. Free (no SMS quota burned); user clicks a link in their email instead.

The new `/email-signup` route handles both signup and login:

1. **Signup**: `authService.signUpWithEmail(email, password)` calls `createUserWithEmailAndPassword` and immediately `sendEmailVerification`. The screen flips to a "Check your inbox" pending state.
2. **Login** (already-verified user): `authService.loginWithEmail(email, password)` → `signInWithEmailAndPassword`. If `user.emailVerified` is `false`, the same pending screen is shown with a "Resend verification email" link.
3. **Check verified**: the pending screen's "I've verified — continue" button calls `getAuth(getApp()).currentUser.reload()` to re-read the server-side `emailVerified` claim. If true, route to `/role-selection`.
4. **Guard**: the `_layout.tsx` redirect effect blocks email/password users whose `emailVerified` is `false` from reaching any screen other than `/email-signup` and `/phone-entry`. Phone OTP users and Google Sign-In users bypass this check entirely (Google auto-verifies; phone OTP uses a verified phone number as the credential).

This flow is documented in the screen header comment at `screens/auth/EmailSignUp.tsx`.

### Step 10 — Firestore rules + indexes

Extend `firebase/firestore.rules`:

```
match /users/{userId} {
  allow create: if isOwner(userId) && request.resource.data.uid == userId;
  allow read:   if isOwner(userId);
  allow update: if isOwner(userId) && request.resource.data.uid == userId;
  allow delete: if false;

  match /tutorProfile/{document=**} {
    allow read:   if isOwner(userId);
    allow write:  if isOwner(userId);
  }
  match /studentProfile/{document=**} {
    allow read:   if isOwner(userId);
    allow write:  if isOwner(userId);
  }
}

match /admins/{adminId} {
  // v1: client-side match against these rules. The client must read the
  // /admins collection to look up the salt and passwordHash. This is
  // INSECURE for production — replace with a Cloud Function that
  // matches the password server-side and returns a customToken
  // (signInWithCustomToken) in v2. Tracked in
  // Documentation/04-Firebase/phase-3-notes.md.
  //
  // For v1 we accept that the entire admins collection is publicly
  // readable. To limit blast radius, the seed script should rotate the
  // passwordHash regularly and the docs should be deleted from this
  // collection before any production release.
  allow read: if true;
  allow write: if false;   // seed only (admin SDK / `firebase deploy --only firestore:rules`)
}
```

`firebase/indexes.json` needs no new indexes (we only do equality lookups, no compound queries).

### Step 12 — Phone+password sign-in (v1: disabled in UI)

Firebase Auth Phone provider does not natively support password (it always uses OTP). A real "phone + password" flow requires either (a) a Cloud Function `signInWithPhonePassword(phone, password) → customToken` that verifies the SHA-256 hash in Firestore and mints a custom token, or (b) a separate `signInWithEmailLink` flow. Both are **out of scope for v1**.

**v1 behavior**: the "Log in" tab still works for admins (email + password) and for users who want to re-auth via OTP. Phone + password is **not exposed in the UI**. The "Log in" tab detects a phone-shaped input and routes through the OTP flow as today. If the user explicitly types a password with a phone-shaped input, the field shows a tooltip: "Phone + password sign-in is coming soon. Use OTP instead." (A small disabled-state microcopy hint, not a hard error.)

**v2 work**: build the `signInWithPhonePassword` Cloud Function. Tracked in `Documentation/04-Firebase/phase-3-notes.md`.
